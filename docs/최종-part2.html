메타 설명(요약문): 금지 공지만으로는 개인 AI 사용이 없어지지 않습니다. 사내 AI 사용률을 올리려면 무엇이 필요한지, 6주 안에 어디까지 준비할 수 있는지, 그중 회사가 직접 해야 하는 일은 무엇인지 정리합니다.

Part 1에서는 사내 AI를 도입하고도 사용률이 오르지 않는 원인을 짚었습니다. 직원이 규정을 몰라서가 아니라, 사내 AI를 써도 배경 설명은 그대로 해야 하는데 접속 대기와 결과 검증만 더 붙기 때문이었습니다. 쓰기 시작하는 데 며칠이 걸리고, 사내 자료를 읽지 못하고, 실제 업무 도구 안에 없고, 결과의 근거를 확인하기 어렵고, 사용 기록도 남지 않는 상태라면, 개인 AI로 우회하는 흐름은 방식만 바뀔 뿐 없어지지 않습니다.

그럼 사용률을 올리려면 무엇이 필요할까요. 여섯 가지입니다. 그중 대부분은 회사가 직접 개발하지 않아도 갖출 수 있습니다.

사내 AI가 통과해야 할 6가지 질문

기능 목록이 아니라 질문 형태로 정리했습니다. 지금 쓰고 계신 사내 AI에 그대로 대입해 보시면 됩니다.

# 확인할 질문 통과 기준 막히면 생기는 일
1 오늘 요청하면 오늘 쓸 수 있나 계정과 권한이 자동으로 발급되고, 승인 대기가 며칠씩 늘어지지 않음 마감이 급하면 개인 계정으로 넘어감
2 정책 문서가 아니라 시스템이 막아주나 민감정보 탐지와 외부 반출 통제가 실제로 작동함 지침만 있고 통제는 없는 상태
3 누가 무엇을 했는지 기록에 남나 사용자, 시각, 입력 자료, 참조 문서, 출력이 기록으로 남음 사고가 나도 경위를 못 밝힘
4 사내 문서를 근거로 답하나 사내 문서와 정책에 연결되고, 문서가 바뀌면 답도 함께 바뀜 현업이 문서를 복사해 외부 도구에 붙여넣음
5 쓰던 업무 도구 안에서 바로 되나 메일, 문서, 티켓, 개발 도구 안에서 실행됨 포털을 따로 여는 순간 사용률이 떨어짐
6 어제 되던 게 오늘도 되나 프롬프트와 지식, 모델을 바꿀 때 승인 절차와 되돌리기 수단이 있음 결과가 한 번 달라지면 현업이 다시 쓰지 않음

여섯 개 중 자신 있게 “예”라고 답하는 항목이 몇 개인지 세어 보시면 현재 수준이 드러납니다. 넷 이하라면 금지 공지를 몇 번 더 내도 결과는 같습니다.

여기서 순서가 중요합니다. 4번과 5번은 성과가 눈에 빨리 보여서 많은 조직이 여기부터 시작합니다. 그런데 1번부터 3번, 6번을 먼저 확정해 두지 않으면 부서마다 다른 예외가 쌓입니다. 나중에는 손댈 수 없을 만큼 복잡해집니다. 기준을 먼저 세우고 업무를 하나씩 붙여야, 적용 범위를 넓혀도 운영 부담이 늘지 않습니다.

6주 일정: 무엇을, 누가 하나

아래 표에서 눈여겨보실 곳은 왼쪽 열이 아니라 맨 오른쪽 열입니다.

주차 하는 일 주로 누가 하나
1주 현황 진단. 어떤 업무에 어떤 도구가 쓰이는지, 사내 AI가 왜 안 쓰이는지 파악 마켓핏랩 진행, 고객사는 현업 인터뷰만 참여
2주 운영 기준 확정. 권한 구조, 데이터 등급과 등급별 허용 범위, 남길 기록 항목 마켓핏랩 설계, 보안과 컴플라이언스 승인
3~4주 업무 3건 파일럿. 실제 업무 흐름 안에 붙이고 현업이 그대로 씀 Articul8 플랫폼 위에서 마켓핏랩 구축
5주 운영 체계 구축. 변경 승인 절차, 문서 갱신 반영, 사용 현황 대시보드 Articul8 기본 기능, 마켓핏랩 설정
6주 확장 기준 확정. 다음 업무로 넓힐 조건과 우선순위 결정 고객사 결정, 마켓핏랩 지원

고객사가 직접 해야 하는 일은 세 가지입니다. 1주차에는 현업 인터뷰에 응하고, 2주차에는 운영 기준을 승인하고, 6주차에는 확장 여부를 결정하시면 됩니다. 기준서 작성과 로그 설계, 파일럿 구축, 대시보드 설정은 저희가 맡습니다.

파일럿 업무 3건은 아무거나 고르지 않습니다. 자주 반복되고, 결과물의 형태가 분명하고, 다루는 자료의 민감도를 통제할 수 있고, 성과를 판정할 기준이 있는 업무를 고릅니다. 품질도 정답률만 보지 않습니다. 현업 승인률과 재작업률, 검증에 걸린 시간을 함께 봅니다.

왜 부분 개선만으로는 같은 문제가 반복되나

많은 조직이 사내 포털을 조금 손보거나 한 부서에만 도구를 더 붙이는 선에서 접근합니다. 그리고 대개 몇 달 뒤 같은 문제를 다시 겪습니다.

권한과 기록 체계를 부서마다 다르게 만들면 예외가 쌓입니다. 예외가 쌓이면 나중에 통합할 때 드는 비용이 처음부터 기준을 세울 때보다 커집니다. 사내 지식 연결이 약하면 현업은 다시 문서를 복사해 외부 도구에 붙여넣습니다. 사내 AI가 업무 도구 안으로 들어가는 시점이 늦어지면 그사이 개인 AI 사용이 습관으로 굳습니다.

여기서 “처음부터 설계한다”는 말은 모델이나 에이전트를 직접 개발한다는 뜻이 아닙니다. 앞의 여섯 가지 조건을 먼저 확정하고, 그다음에 적용할 업무를 빠르게 늘린다는 뜻입니다.

Articul8은 무엇이 다른가

여섯 가지 조건을 회사가 직접 갖추는 방법도 있습니다. 다만 그때 무엇을 감당해야 하는지는 알고 시작하는 편이 좋습니다.

확인할 조건 범용 AI 도구로 직접 구축할 때 Articul8
데이터가 어디서 처리되나 외부 API로 나감. 정책 문서로만 통제 고객사 보안 경계(VPC) 안에서 100% 실행
사내 문서를 근거로 답하게 하려면 검색과 연결 파이프라인을 직접 만들고 계속 관리 산업별로 미리 학습된 모델군 제공 (제조 공급망 등)
여러 모델과 에이전트 연결 어느 상황에 무엇을 쓸지 규칙을 사람이 다 작성 ModelMesh가 별도 규칙 작성 없이 요청에 맞는 경로를 자동 선택
기록과 감사 대응 로그 수집 체계를 따로 구축 출력에 추적·감사 기록이 기본으로 남음
도입 기간과 비용 사내 인력 투입, 기간 예측이 어려움 배포 기간 4배 단축, 총소유비용 3~5배 절감

수치와 기능은 Articul8 본사 공개 자료 기준입니다.

Part 1에서 짚은 문제 중 가장 큰 문제는 데이터였습니다. 직원이 계약서를 개인 챗봇에 올리는 순간, 그 문서가 어디서 처리되는지 회사는 알 수 없습니다. 위 표의 첫 번째 항목이 이 문제에 대한 답입니다. 모델이 고객사 보안 경계 안에서 실행되면 사내 문서를 넣어도 자료가 밖으로 나가지 않습니다. 감사 로그가 기본으로 남으면 “누가 무엇을 했는지”에 답할 수 있습니다.

막는 접근과 쓰게 만드는 접근은 여기서 갈립니다. 현업이 원하는 것은 사용 허가가 아니라 그날 안에 일이 끝나는 것입니다. 회사에 필요한 것은 그 과정이 기록으로 남는 것입니다. 둘을 동시에 만족하는 방식이 개인 AI보다 쓰기 편해지면, 금지 공지 없이도 직원들이 사내 AI로 돌아옵니다.
